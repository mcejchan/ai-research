## Verified finding

### Quiz publication has three divergent acceptance mechanisms, and the deployed one fails open

**Problem**

The quiz has three independently owned notions of acceptable content:

1. `quiz/build-index.test.js` tests index metadata behavior.
2. `quiz/build-index.js` parses and publishes the catalog, but catches every bad level read/parse and continues.
3. `quiz/validate-quiz.js` performs schema and quality validation, but no test gate or deployment invokes it.

The Pages workflow adds a fourth spelling of the boundary by directly running the focused test and tolerant builder. The root `Makefile:test` is documented as the authoritative repository gate, but it also only runs the focused builder test—not validation.

**Evidence**

- Root `README.md` calls `make test` the authoritative repository test gate.
- Root `Makefile:test` invokes `node --test quiz/build-index.test.js` but never `quiz/validate-quiz.js`.
- `.github/workflows/deploy-quiz.yml:29-33` directly runs the same focused test, then `node quiz/build-index.js` and publishes `quiz/`.
- `quiz/build-index.js:50-56` catches read and JSON parse failures, logs `Skipping invalid level ...`, and continues to write a successful index. Therefore a malformed tracked level is omitted from the published catalog instead of blocking publication.
- `quiz/build-index.test.js` contains two tests and no malformed-level/fail-closed case.
- `git grep validate-quiz` finds only the validator itself; it has no caller.
- Git history shows the tolerant builder dates to May and the deployment-only test was added in July; the validation and publish boundaries were never unified.
- Current verification is green despite the missing integration: focused quiz test passed 2/2; full `make test` passed quiz 2, viewer 2, command contracts 4, and Python 42.

**Impact**

A malformed or structurally invalid level can produce a green deployment that silently publishes a partial quiz catalog. Maintainers must remember which of three mechanisms to run, and future schema changes can update one authority without the others. The operational signal is especially misleading: successful deployment does not mean all source levels were accepted.

**Recommendation**

Create one explicit, fail-closed quiz publication contract—preferably a single project command/Make target that:

1. validates every source level,
2. builds the index without swallowing malformed input,
3. runs the small static-runtime test.

Make both root `make test` and Pages call that same command. Keep Pages scoped to quiz files; do **not** make static-site publication depend on unrelated viewer or Python pipeline tests. The simplification is one shared quiz boundary, not one giant repository-wide deployment gate.

If quality/bias warnings are intentionally non-blocking, separate them from structural errors in the same validator contract. Structural parse/schema failures should stop publication; advisory heuristics may remain warnings. This avoids replacing today's ambiguity with an overly strict deploy policy.

## Rejected hypotheses

## Self-critique

The builder's tolerant behavior could be useful for an interactive local catalog over partially corrupt external data. That reading does not fit this path: the inputs are tracked deployment assets, and silent omission changes the published product. Still, wiring the current validator wholesale could block deploys on opinionated bias thresholds, shifting complexity into policy exceptions. The recommended boundary therefore distinguishes hard parse/schema integrity from advisory content-quality checks.

A shared command adds one named wrapper, but removes independently maintained workflow commands and the dead validator seam. It should remain a thin command over existing scripts, not become a new orchestration framework.
