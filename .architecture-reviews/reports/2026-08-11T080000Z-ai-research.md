## Verified findings

### 1. Failed analysis and completed analysis share one product artifact and one success status

**Problem.** The pipeline has two semantically different producers for `analysis_main.md`: actual model output and a placeholder created after any analysis exception. Downstream components use filename existence as the authority for successful analysis, so the fallback erases the distinction it needs consumers to understand.

**Evidence.** `youtube-transcript-pipeline/src/yt_pipeline.py:226-255` catches every exception around model invocation and analysis upload, then writes a success-shaped placeholder to `analysis_main.md`. `test/test_yt_pipeline.py:253-279` deliberately preserves this as expected behavior. `yt-viewer/server.js:77-81` sets `hasAnalysis` solely with `files.includes("analysis_main.md")`, so both outcomes become `true`; its analysis endpoint serves either body under the same route. The repository README and pipeline README describe `analysis_main.md` as LLM analysis. The `mindmap`, `kb-index`, `expand-analysis`, and `flashcards` command contracts likewise consume that filename as structured analysis or a draft to enrich. A repository scan found a real placeholder at `local-knowledge-base/youtube/futurecast-technologie-zitrka/2026-05-19_artemis-ii-prvni-lide-miri-k-mesici-jsme-blizko-meziplanetarni-civilizaci/analysis_main.md`, so this is not merely a theoretical test state. Git history shows the placeholder dates to the initial pipeline commit, while viewer existence semantics arrived later without a shared completion contract.

**Impact.** Viewer/API status reports analysis as available when enrichment failed. Knowledge commands can ingest or transform a retry notice as if it were analysis, and operators cannot select missing analyses for retry by checking the canonical artifact. The design appears to avoid a lifecycle state, but merely hides it inside document content and forces every consumer to infer semantics independently.

**Recommendation.** Reserve `analysis_main.md` for completed analysis. If optional enrichment fails, keep the successful transcript and leave analysis absent—the viewer already has `hasAnalysis: false` and returns 404 for a missing file. Preserve the diagnostic in logs or in existing operational retry evidence, not as product content under the success filename. Do not add a manifest or an analysis state machine unless a concrete retry workflow proves absence insufficient. Before implementation, contract-test that every knowledge consumer handles a missing analysis rather than assuming universal presence.

## Recommendations

1. Make `analysis_main.md` a truthful single authority: presence means completed analysis; absence means unavailable/pending enrichment.
2. Keep transcript capture independent from optional analysis failure; do not make the entire ingestion fail closed.
3. Add focused producer/viewer/consumer contract tests around missing analysis before removing the placeholder.
4. Discuss the still-open explicit storage backend recommendation from the 2026-07-31 report separately; it is independent of this finding.

## Self-critique

A placeholder can be convenient for humans browsing the filesystem, and optional analysis should not invalidate a successfully captured transcript. However, using the completed-analysis filename for that notice makes convenience depend on a false shared contract. Making analysis failure fatal would overcorrect and couple two legitimately separate stages. Adding `analysis_status.json`, retry markers, or several lifecycle values would also shift the complexity into another authority. The recommended absence semantics reuse a state the viewer already represents and remove an artifact rather than introduce one. Its main risk is that some knowledge commands assume every folder has analysis; the repository search shows both assumptions and at least one missing-file fallback, so implementation must pin all consumers before changing behavior.
