## Rejected hypotheses

### Root, component, and Pages checks are competing test authorities

Rejected. The root `make test` target is the repository-wide gate, while component commands are narrower boundaries used for focused work. Pages correctly calls `make quiz-publication-check` rather than duplicating its implementation or coupling static publication to the viewer and Python pipeline. This is layered scope, not competing ownership.

### Quiz validation still has multiple acceptance authorities

Rejected. The remediation after the previous review established one executable publication contract. `quiz/build-index.js` imports `validateLevelData` from `quiz/validate-quiz.js`, malformed/schema-invalid input fails before writing a partial index, and both root testing and Pages delegate to the same `quiz-publication-check` target. Advisory bias policy remains deliberately non-blocking and is tested as such.

### Generated quiz index is a second source of product truth

Rejected. `quiz/levels/index.json` is derived static metadata for a serverless runtime, generated by the same fail-closed publication command. Rebuilding it produced a byte-identical tracked result. It is a deployment artifact with one generator, not an independent acceptance policy.

### Viewer and static quiz should be merged

Rejected. They serve different runtime and deployment boundaries: one browses the local knowledge tree, while the other is a static Pages application. Combining them would increase coupling and blast radius without removing a duplicated authority.

### Different missing-analysis behavior in knowledge commands is policy drift

Rejected. Tests deliberately pin different operations: indexing may include transcript-only content without broken analysis links, while analysis-dependent commands skip or stop before accessing a missing file. The distinction follows consumer capability rather than duplicate state ownership.

### Drive-to-local fallback is a new finding

Rejected as new. The behavior remains architecturally questionable, but it is unchanged and already documented with evidence and a concrete recommendation in `/Users/michal/Projects/ai-research/.architecture-reviews/reports/2026-07-31T080000Z-ai-research.md`. No new call path, regression, or damage was found in this run.

### Permissive URL/video-ID normalization creates a parallel identity authority

Not substantiated. `extract_video_id()` accepts common YouTube forms and falls back permissively, but the actual metadata boundary rejects invalid/nonexistent IDs. Tests cover accepted URL forms and failure propagation. This may merit stricter input validation on usability grounds, but no second persisted identity, divergent downstream state, or concrete simplification payoff was demonstrated.

Rejected by design. These are intentional agent artifacts, and no accidental product publication, runtime dependency, source collision, or unbounded consumerless growth was demonstrated. Known cache/tmp observations also had no new product churn since the prior review.

## Self-critique

A green test suite cannot prove that no simplification opportunity exists; it only confirms the inspected contracts behave as encoded. The strongest remaining candidate—the storage fallback—does represent hidden backend switching, but reporting unchanged evidence again would inflate the ledger and imply a newly discovered problem. Conversely, collapsing local and Drive storage entirely would erase a legitimate offline boundary; the sound prior recommendation removes implicit selection, not either backend.

Likewise, one giant repository command used everywhere might look simpler numerically, but making Pages depend on unrelated viewer and Python suites would transfer complexity into deployment coupling. The present hierarchy is justified because the shared quiz acceptance logic has one owner and broader gates compose it.

The URL parser is permissive enough to invite cleanup, but stricter parsing would mainly relocate validation and compatibility cases. Without evidence of ambiguous persisted IDs or masked successful processing, that is hygiene rather than architecture simplification.
